# 野生动物红外相机照片索引服务

面向物种识别模型训练的数据整理工具：研究员分批上传红外相机照片 CSV，服务把
**同一次出没**的照片传递归组，按组稳定划分训练/验证索引，每批新增照片发布一个
**不可变版本**（两份可下载索引 + 版本号）。

技术栈：FastAPI + SQLite（WAL），单容器即可运行。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据（SQLite 库 + 各版本索引文件）持久化在命名卷 `wildlife-data` 中，容器重建不丢。

## 浏览器演示：跨批补传与撤回样例

首页可直接下载 `samples/` 下的五个样例 CSV（仓库目录 `samples/` 中也有），按顺序操作：

| 步骤 | 上传文件 | 预期结果 |
|---|---|---|
| 1 | `batch1_base.csv` | 发布 **v1**：6 张 / 4 组。CAM01 两段出没间隔 70 秒 > 60，分为两组 |
| 2 | `batch2_backfill.csv` | 发布 **v2**：补传的 P0007（08:01:05）距前后两组各 35 秒，把 CAM01 旧两组**合并**；P0008 加入 CAM02 旧组；P0009 新相机新组。全库重新归组 |
| 3 | `batch3_duplicate.csv` | 与 batch2 完全同号同内容 → **不产生新版本**（noop） |
| 4 | `batch4_conflict.csv` | P0001 物种被改动 → **整批拒绝**（含其中的新照片 P0011），现役版本保持 v2 |
| 5 | `batch5_retract.csv`（撤回表单） | 撤回 P0007、P0009 → 发布 **v3**：现役索引移除两张并重新归组（CAM01 因桥接照片 P0007 被撤回重新分裂成两组）。v1 不含撤回照片仍可下载；v2 含 P0007/P0009，两份索引下载均被禁用 |
| 6 | 再次上传 `batch5_retract.csv` | **重复撤回**：不产生新版本 |
| 7 | 自行构造含 P0009 的上传批次 | **整批拒绝**：含禁入编号 |

任意时刻打开 v1 的下载链接，内容保持最初发布时的原样（版本不可变）；但若某版本包含
已撤回照片，其两份索引下载会被拒绝（见下文「撤回与禁入清单」）。
首页「版本历史」可进入每个版本查看分组明细，「批次记录」查看每批的处理结果与拒绝原因。

## 撤回与禁入清单

浏览器首页「撤回照片（禁入清单）」表单上传只含 `photo_no` 一列的 CSV（其他列忽略）：

```csv
photo_no
P0007
P0009
```

- **在库照片**从现役索引中移除并基于剩余照片重新归组，发布新版本（`v3` 起）。
- **未入库编号**同样写入永久禁入清单，防止迟到的补传把它带进索引。
- **重复撤回**（所有编号都已在禁入清单且不在库）记 `noop`，不产生新版本。
- **迟到补传**：上传批次只要包含任一禁入编号，整批 `rejected`（同批其他新照片也不入库）。
- **历史版本下载**：发布时把版本成员写入 `version_photos`；下载时若版本含任一禁入照片，
  `train_index.csv` / `val_index.csv` 均返回 **403**。未受影响的旧版本保持可下载且内容不变。
- **原子性**：禁入登记、照片删除、索引文件落盘、`versions` 行、版本成员、`active_version`
  指针在同一 `BEGIN IMMEDIATE` 事务中提交；任何一步失败整体回滚，禁入清单、现役索引和
  下载权限都不会出现部分撤回状态。下载与页面读取同一 WAL 读快照，新发起的下载不会取得
  已撤回照片。
- 首页列出禁入清单及登记批次；撤回批次在「批次记录」中类型标为「撤回」，可查看每条编号
  当时是否在库。

## CSV 格式

必需列（顺序不限，表头名需一致，UTF-8 编码）：

```csv
photo_no,camera_no,captured_at,species,rel_path
P0002,CAM01,2026-03-01T08:00:00Z,wild_boar,cam01/20260301/P0002.jpg
```

- `captured_at`：UTC 拍摄时间，ISO8601（`2026-03-01T08:00:00Z`；带时区偏移会换算为 UTC，无时区按 UTC 处理）
- 任何一行校验失败（缺列、时间为空/无法解析等）→ **整批拒绝**，库内不产生任何变化

## 归组与划分规则

1. **归组**：同一 `camera_no` 内按 `(拍摄时间, 照片号)` 排序，相邻间隔 ≤ 60 秒
   （`GAP_SECONDS` 可调）即同组，分组可传递（链式桥接的照片同属一组）。
2. **组标识**：`group_id` = 组内最早照片的照片号。补传合并两组时沿用更早组的标识；
   若补传照片比组内最早照片还早，组标识随之改变。
3. **划分**：按组整体划分（同一出没事件不会泄漏到训练/验证两侧），
   `sha256(SPLIT_SALT | group_id) % 100 < VAL_PERCENT` → 验证集。
   完全确定：同样的照片集合无论分几批、以什么顺序入库，最终划分一致。

## 版本与一致性设计

- **发布原子性**：照片入库、索引文件落盘（先写 `.tmp-*` 目录再 `rename` 原子生效）、
  `versions` 行、版本成员表、`active_version` 指针在同一个 `BEGIN IMMEDIATE` 事务中提交。
  任一步失败整体回滚并清理半成品目录，**现役版本不变**；失败批次留有审计记录。
- **并发**：SQLite 写事务把交错上传/撤回（含多进程）串行化，后提交者基于前者已发布的
  状态继续；读者（页面/下载）走 WAL 快照，不被写入阻塞。页面展示的现役版本、禁入清单与
  两份下载始终对应同一完整版本。
- **不可变版本**：`data/versions/v{N}/` 一旦发布永不修改，旧链接在未被撤回影响时永远
  下载原内容；含撤回照片的版本下载被 403 拒绝，原始文件留存以备审计。
- **幂等**：同号同内容重投 → 批次记 `noop`，不产生新版本；
  同号异内容 → 整批 `rejected`；重复撤回 → `noop`。

## 升级现有库

服务启动时自动做幂等迁移：给旧 `batches` 表补 `kind` 列，新建 `retractions` /
`version_photos` 表，并按已发布的不可变索引文件回填历史版本成员关系，
因此旧库升级后撤回也能正确禁用受影响的历史版本下载。

## 本地开发与测试

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest tests/ -q          # 32 个测试：归组逻辑 + 端到端（含并发、发布失败回滚、撤回/禁入/旧版下载权限）
DATA_DIR=./data SAMPLES_DIR=./samples uvicorn app.main:app --reload
```

## 配置项（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `DATA_DIR` | `./data`（容器内 `/data`） | SQLite 与版本索引存放目录 |
| `SAMPLES_DIR` | `./samples` | 样例 CSV 目录（存在时首页显示演示入口） |
| `VAL_PERCENT` | `20` | 验证集目标比例（按组分桶） |
| `GAP_SECONDS` | `60` | 同相机相邻照片归组阈值（秒） |
| `SPLIT_SALT` | `wildlife-trap-v1` | 划分哈希盐；改盐整体重排训练/验证划分 |

## 项目结构

```
app/
  main.py        # FastAPI 应用：上传、撤回、版本发布、页面、下载（含事务与落盘逻辑）
  grouping.py    # 归组与稳定划分（纯函数，可单测）
samples/         # 跨批补传 + 撤回演示的五个样例 CSV
tests/           # 单元测试 + 端到端测试（含撤回与禁入清单）
Dockerfile
docker-compose.yml
```
